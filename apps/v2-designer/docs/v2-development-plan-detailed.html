01

目标与约束

1.1 项目目标

  • 把 apps/v2-designer 建成稳定可用的工业大屏设计器。
  • 打通 v2-designer -> v2-renderer 发布链路。
  • 将当前分散实现升级为可测试、可演进工程体系。

1.2 当前硬约束

  • 技术栈固定：Vue3 + Pinia + X6 + x6-vue-shape + Vite。
  • 当前仓库不含后端服务实现。
  • docs/* 被忽略，正式文档需放在应用目录。

1.3 本方案不覆盖

  • NestJS/DB/RBAC/多租户、协同服务端、云原生部署实现。
02

仓库现状审计（As-Is）

Monorepo 现状

  • apps/v1-designer：相对完整，可复用能力多。
  • apps/v2-designer：主建设目标，编辑器核心可用。
  • apps/v2-renderer：当前仍为占位页。

包层现状

  • packages/core：有 schema 类型，engine/canvas 仍 TODO。
  • packages/v2-shared：有类型/常量/校验，与运行态仍有差距。
  • packages/ui：可复用组件沉淀不足。

关键技术债

  • 坐标系统仍脆弱（外部缩放 + 重写转换函数）。
  • 图元列表与注册表存在漂移风险。
  • 导出逻辑与 store 字段存在不一致风险。
  • renderer 未接入真实 schema，发布链路未闭环。
  • v2 自动化测试缺失。
03

To-Be 总体架构

L1 App→ v2-designer / v2-renderer→ L2 Domain→ v2-shared (adapter/validator/registry)→ L3 Core→ schema / engine / utils

核心原则

  • 编辑态真相：X6 JSON；发布态真相：Schema v2.1。
  • 显式双向转换，不在 UI 层拼装发布 schema。
  • 先建后删，确保交互失败可恢复。
  • 图元与连线统一注册清单，禁止多源定义。
04

数据模型与 Schema 策略

决策

  • D1：编辑态继续使用 graph.toJSON()/fromJSON()。
  • D2：新增 toSchemaV2 / fromSchemaV2 转换器。
  • D3：发布导出仅接受 CanvasSchema v2.1。

覆盖路线

阶段覆盖范围目标
MVP基础节点/连线/端口/画布可导出可回导
Phase 2动画、状态映射、变量事件运行一致
Phase 3数据源绑定、资源索引发布可用
05

坐标系统与视口模型

规范

  • 统一左上角原点 + 像素坐标。
  • 缩放仅影响视觉，不改逻辑坐标。

改造点

viewport-adapter.ts (planned)
clientToCanvasPoint(rect, scroll, zoom, padding, clientPoint)
canvasToClientPoint(rect, scroll, zoom, padding, canvasPoint)
getVisibleCanvasRect(rect, scroll, zoom, padding)

验收

  • 四角拖拽无异常，缩放 0.1~5 误差 <= 1px。
